# Cloud job discovery

The user requested that searches continue while the operator computer is off. The design extends the existing Vercel worker project with a private career-discovery queue consumer. Vercel Queues is currently beta. It is available on demand without a continuously provisioned idle worker. CV evaluation/tailoring stays on local Ollama; cloud AI remains disabled.

The authenticated frontend inserts the existing discovery_runs record before calling the existing secret-protected worker wake route with only discoveryId. Queued, authorized result reads retry failed notifications; publish idempotency uses the run ID with one-hour retention and a five-minute deduplication bucket (queued reads can recover an exhausted delivery). No filter, tenant, URL, executable or CV is accepted by the wake handler. Queue callbacks are authenticated by Vercel infrastructure. The consumer only claims the specified UUID through migration 017’s security-definer RPCs. One concurrent consumer plus SQL atomic claims handles duplicate/replayed deliveries. Exact claim/lease checks, heartbeat loss, cancellation/account-block deletion and expiry fence publication. Interrupted scans fail visibly rather than silently retrying the scanner indefinitely. Existing rate limits/expiry remain.

The dedicated career_discovery role has only schema usage and three RPC grants, with no direct search/profile/CV/auth/job table access. Runtime uses DISCOVERY_DATABASE_URL and requires that role, Neon hostname and verify-full TLS. Provision the credential privately; never print/commit it. Existing worker project credentials for disabled legacy cloud AI are not used by discovery. The scanner child inherits an explicit noncredential environment, reads only generated search filters and writes its exact temporary child directory. It uses the same root scanner/provider transport, date/link/authorization gates and 50-job/2MB output bounds. Child timeout is 225 seconds within a 300-second queue function; close precedes scratch cleanup. No extra model/provider keys are added.

Build preparation follows relative ESM imports from fixed scanner/runner entries into a hashed 103-file source capsule. Only .mjs code files plus the explicitly allowlisted shipped tracker-aliases.json are permitted, with personal/data/config directories rejected. Literal external packages are allowlisted (YAML/HTTP/config plus the unused optional browser import); no browser package/binary is installed. Next traces include the exact raw capsule and required runtime libraries. Build audits retain existing route/source/private-file boundaries. No user CV, tracker, environment file or arbitrary directory is copied. The child runs raw source to preserve CLI module identity.

HOSTED_DISCOVERY_CLOUD_ENABLED is separate in frontend and worker production configuration. Worker can be installed first while frontend remains local. After successful cloud-only proof with the local discovery task stopped, enable frontend dispatch and truthful cloud UI copy, deploy, and repeat the real browser flow. Keep the local AI task unchanged. Rollback: turn frontend cloud discovery off, deploy, ensure no active cloud search, then restart the existing local discovery task; never kill a scan merely because it is old. Source/schema deployment alone is not evidence of live cutover.

Verification: unit body/role/flag/notification tests; isolated PostgreSQL no-table/CV grants, denied web claims, exact concurrent/replayed delivery, cancellation, stale tokens, expired leases and bounded result payloads; production Next/Playwright regression including existing CV/PDF journey. Live deployment/cutover evidence is recorded in PROJECT_HANDOFF.md separately.

References: [Vercel Queues](https://vercel.com/docs/queues), [delivery/security concepts](https://vercel.com/docs/queues/concepts), [function limits](https://vercel.com/docs/functions/limitations). Continuous Daemons were considered but consume provisioned-memory quota while idle; on-demand queued functions fit the current bounded scanner.

Initial cloud-only proof uncovered a missing static scanner asset (tracker-aliases.json) before any database claim. The asset is now explicitly allowlisted/hashed; raw capsule import and CLI help pass, and a subprocess regression guards it. Sanitized receipt/start/failure events now make queue-level retries observable. No user data file is added. Live verification remains pending until the corrected cloud deployment processes the synthetic request.
