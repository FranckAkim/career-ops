# Operator-reviewed durable snapshot fences

Migration 013 and `SnapshotFencer` add a private operator capability for generation-aware snapshots with durable pre-upload provenance. Neither runtime role can access the fence ledger. No public endpoint, automatic verifier or deletion button is added.

The operator must first block the account and review exact request/snapshot/generation/inventory/capture scope. The service requires explicit `FENCE SNAPSHOT CONTENT` confirmation, an exact review hash, evidence hash, a trusted actual-runtime drain verifier and an independent trusted immutable-writer verifier bound to that scope/evidence. Unknown provenance, legacy inventory, shared/foreign references, active requests/captures/jobs/attempts and stale scopes refuse fencing. No automatic provider settlement inference is made.

Tenant/user/request/snapshot locks serialize the start and foreign-reference check. Starting a fence durably transitions the request and object to `fencing`; cancellation is then unavailable. Immutable snapshot-reference guards reject new references. A ledger freezes generation, exact file hashes, review/evidence hashes and per-key progress before any content replacement. Each key is conditionally sealed with a retained marker, verified before progress advances, and the manifest is last. Lost responses/restarts retry safely. All keys must verify before the object/ledger become `fenced`. No marker is deleted by that path.

Account purge accepts a failed capture only when that same deletion request has a completed fence ledger and a fenced object. It preserves fenced objects, verifies their marker bytes outside database locks, rechecks ledger scope in the final transaction and reports retainedFencedSnapshots on completion/replay. Other unfinished/legacy/unknown captures retain their existing barriers. Direct finalization without prepared `purging` state is rejected. Ordinary ready-snapshot purge retains its existing exact-key deletion behavior.

The fence changes stored content, so operator cancellation cannot restore it. Minimal storage keys/content-hash metadata, markers and opaque audit records remain intentionally. This does not erase prior downloads, provider cache copies/backups/logs or authorize unconditional privileged writers. Do not describe fenced objects as physically absent. The caller must supply genuine immutable-writer/runtime evidence; a callback returning true is used only in deterministic tests, never as a production default.

The full disposable PostgreSQL suite verifies proof/drain refusal, stale scope, foreign-reference races, publication exclusion, no cancellation, outage/lost reply, progress/restart, late immutable-create rejection, fresh identical-content generation, role isolation and final fenced-account cleanup without marker deletion. All 47 unit tests and hosted typecheck pass. Production migration 013 is installed with no runtime ledger grants; no real account was fenced. Fresh synthetic provider proof and final source CI are recorded separately in the shared handoff.
